|---|---|---|

| 公共函数（pub fn）数 | **240+ 个** | grep 统计 |

**结论**：这不是玩具项目，是一个**已经过 1 年实际打磨、代码体量接近商用产品级**的 Rust 数据网关。后续平台化的可行性主要看"如何让现有能力被更多角色（不只超管）使用"，而不是"造新引擎"。

### 1.3 关键观察（决定可行性判断）

1. **Auto API 4500 行是项目核心资产**：CRUD + 事务 + RPC + 复杂查询语法（eq/gt/lt/like/in/is/order/limit/offset/select），是平台化叙事的"主供水管"
2. **RBAC 1770 行 + Auto API 联动已闭环**：DSL 化的行/列条件、API Key scope、参数化绑定防注入——这是 Supabase RLS 的应用层等价物，且性能更好
3. **多租户 1837 行 + 动态连接池**：一个实例可以同时管多个 PG 库，每个库可独立的 RBAC/审计/缓存/Webhook，这是平台化的天然底座
4. **Webhook + Realtime + 审计 共 2074 行**：数据变更出口能力齐全，逆向 ETL / 实时推送 / 合规 不是空中楼阁
5. **缺位的地方**：
   - 前端只有"超管控制台"，没有"项目工作空间"或"开发者工作台"
   - 没有任何"自助开通 / 引导 / 模板"流程
   - 没有项目维度的大盘聚合（数据齐，但没人画图）
   - 没有外部插件 / Hook / 扩展机制
   - 没有 LLM / RAG / 向量检索的任何代码

## 2. 候选平台型方向（10 个，独立评估）

### 评估模板说明

每个候选用以下统一字段评估：
- **一句话定位**：用户能读懂的目标
- **谁会用**：目标角色
- **存量利用**：能复用的具体模块（行数百分比）
- **增量工程**：要新写的功能清单
- **工程量**：粗估人月（按 2 人小队）
- **风险**：主要技术 / 产品风险
- **协同**：与其他候选的关系

---

### 候选 1：零代码后端平台（BaaS）

- **一句话定位**：开发者建表 → 自动获得 REST API + 鉴权 + 审计 + Webhook，无需写后端代码
- **谁会用**：内部开发者、独立产品团队、原型开发场景
- **存量利用**：Auto API（100%）+ RBAC（100% 后端）+ 多租户（100%）+ 审计（100%）+ Webhook（100%）+ 缓存（100%）= **8000+ 行内核完全复用**
- **增量工程**：
  - 项目工作空间前端（新建表 / 配权限 / 看大盘 / 配 Webhook）
  - 自助开通向导（5 步引导）
  - 表设计器（DDL 可视化生成）
  - 项目模板（空白 / 博客 / 任务 / 社区 4 套预设）
  - 内置角色（project_owner/developer/viewer）+ 邀请成员
- **工程量**：**2-3 人月**（其中 70% 是前端）
- **风险**：
  - 表设计器复杂度（要不要支持 PG 高级类型 JSONB/Array/Enum）
  - 现有超管控制台与新工作空间的路由 / 权限边界
- **协同**：是 #2、#3、#4、#5 的"主入口"，建议作为底座

---

### 候选 2：PG 数据库治理平台（DBaaS Lite）

- **一句话定位**：客户已有的多个 PG 库 → 挂上来 → 统一获得 SQL Studio + 监控 + 慢查询 + 索引管理 + 审计
- **谁会用**：DBA、运维同事、需要查数据的业务方
- **存量利用**：Schema/Index handlers（100%）+ 多租户连接池（100%）+ 审计 + 监控 + 慢查询 + 主动 kill 查询的 `/api/query-perf/active/:pid/cancel`（100%）+ 数据导出（100%）= **3500+ 行完整复用**
- **增量工程**：
  - 多库连接拓扑可视化
  - SQL Studio 增强（语法高亮、历史、保存的查询、解释计划）
  - 慢查询日历视图 + 趋势图
  - 索引建议（可与 #6 AI 联动）
  - 备份 / 恢复编排（**这块要新做，PG 备份不是 OneBase 现有职责**）
- **工程量**：**2-2.5 人月**（不含备份恢复）
- **风险**：
  - 备份恢复涉及 PG 运维，要不要做需先决定（建议不做，让客户用 pg_dump / pgBackRest）
  - 多库统一视角下的权限模型要重新设计
- **协同**：与 #1 互补（#1 给开发者，#2 给运维）；与 #3 共享审计数据

---

### 候选 3：数据访问审计与合规中台

- **一句话定位**：所有对数据库的访问统一审计 → 异常检测 + 合规报表 + 敏感字段标签
- **谁会用**：安全 / 合规 / 内审团队
- **存量利用**：audit_handlers + audit_middleware（100%，已经在每个请求上）+ slow_queries 表 + RBAC（用于敏感字段标签）= **1000+ 行**
- **增量工程**：
  - 异常访问告警规则引擎（非工作时间访问 / 跨项目访问尝试 / API Key 滥用 / 大批量导出）
  - 敏感字段打标系统（PII / 密钥 / 手机号自动识别）
  - 合规报表模板（等保 2.0 / SOC2 / GDPR 范例）
  - 审计日志归档与查询优化（量大时需要分区）
  - 通知渠道（邮件 / 企微 / Slack）
- **工程量**：**1.5-2 人月**
- **风险**：
  - 异常检测规则的准确率需要数据沉淀
  - 审计日志量大时的存储与查询性能（需早做分区表设计）
- **协同**：可独立成立，也可作为 #1 的子模块

---

### 候选 4：数据 API 资产 / 共享平台

- **一句话定位**：把数据库的表"发布"成有目录、有配额、有计量的 API 资产 → 跨部门 / 对外可控分享
- **谁会用**：数据中台团队、需要对外开放数据的业务方
- **存量利用**：Auto API + API Key（已有 scope 机制）+ RateLimiter（按 tenant）+ Webhook（订阅通知）+ 审计 = **5000+ 行**
- **增量工程**：
  - 资产目录（标题/描述/责任人/字段说明 / 示例）
  - 申请订阅流程（申请 → 审批 → 发放 API Key）
  - 计量大盘（按订阅方、按资产、按时段）
  - SLA 配置（QPS 上限、缓存策略）
  - SDK 自动生成（TS/Python，从 schema 推导）
- **工程量**：**2.5-3 人月**
- **风险**：
  - 审批流引擎要不要自研（建议轻量自研，不引入 Activiti 等重型）
  - 与企业现有 API 网关（Apigee / Kong）的边界
- **协同**：依赖 #1 的项目模型；可独立运营

---

### 候选 5：逆向 ETL / 数据广播平台

- **一句话定位**：数据库写入事件 → 自动推送到下游（Webhook / Kafka / WebSocket / Slack / 邮件）
- **谁会用**：需要"数据库为事件源"的应用、跨系统集成场景
- **存量利用**：webhook_manager + webhook_handlers + events + realtime + redis_pubsub = **1000+ 行**
- **增量工程**：
  - 多种目的地适配器（当前只有 HTTP Webhook，需加 Kafka/RabbitMQ/MQTT/Slack/Email）
  - 转换 DSL（字段映射 / 过滤 / 富化，建议用 JSONata 或类似轻量表达式）
  - 投递可靠性增强（DLQ / 死信队列 / 重试策略 / 消息去重）
  - 订阅管理 UI
- **工程量**：**2-2.5 人月**
- **风险**：
  - 高吞吐场景下 Webhook 性能（建议引入消息队列做缓冲，但这又增加部署复杂度）
  - 转换 DSL 要不要支持脚本（lua / wasm）会显著影响复杂度
- **协同**：可独立；与 #4 共享配额 / 计量基础设施

---

### 候选 6：AI 数据助手（NL2SQL + 慢查询诊断）

- **一句话定位**：自然语言问数据 → AI 生成 SQL → 安全闸 → 执行 → 结果可视化；慢查询自动给优化建议
- **谁会用**：业务方（不会 SQL）+ DBA（要找慢查询根因）
- **存量利用**：schema_handlers（提供 schema 上下文）+ `/query` 端点（执行 SQL）+ slow_queries 表 + RBAC（限制 AI 生成的 SQL 受权限约束）+ audit（记录 AI 调用）= **3000+ 行间接支撑**
- **增量工程**：
  - LLM Adapter trait（v1 实现 OpenAI 兼容协议，覆盖 OpenAI/DeepSeek/vLLM/Ollama）
  - Schema 元数据 RAG（向量化建表语句和注释，用于 prompt 召回）
  - 安全闸（默认只读、写操作要二次确认、敏感字段 mask、token 配额）
  - AI 对话 UI（前端聊天 + SQL 预览 + 执行按钮）
  - 慢查询诊断专用 prompt（输入 EXPLAIN + 表结构 + 慢语句）
- **工程量**：**2-2.5 人月**
- **风险**：
  - LLM 输出的 SQL 准确率（需要充足的 schema 上下文 + few-shot examples）
  - 私有化客户处的 LLM 可用性（需要支持自部署）
  - 向量数据库选型（pgvector 最省事，避免引入新服务）
- **协同**：是横向能力，可叠加在 #1-#5 任意一个上

---

### 候选 7：统一身份 / SSO 中台

- **一句话定位**：OneBase 的身份模块独立成产品 → 给客户其它系统提供统一登录 / SSO / 用户目录
- **谁会用**：客户的多个内部系统（不只是 OneBase）
- **存量利用**：auth + auth_handlers + sso（OIDC + Google/FB/GitHub）+ session 吊销 = **1700+ 行**
- **增量工程**：
  - SAML 2.0 支持（企业 IdP 必须）
  - LDAP / AD 集成（同步用户和组）
  - 标准 OIDC Provider 模式（让 OneBase 自己做 IdP，给其它应用发 token）
  - 用户目录 + 组管理
  - MFA（TOTP / WebAuthn）
- **工程量**：**3-4 人月**（SAML 和 LDAP 都不简单）
- **风险**：
  - 偏离 OneBase 主航道（数据网关 vs 身份）
  - 与已有 SSO 产品（Keycloak / Authing）竞争激烈
- **协同**：与 #1-#6 都可用，但作为独立产品意义不大

---

### 候选 8：Headless CMS

- **一句话定位**：把 Auto API + RBAC + 审计 包装成内容管理界面 → 编辑 / 审核 / 发布 / 媒体库
- **谁会用**：内容运营、市场、产品文档团队
- **存量利用**：Auto API（100%）+ RBAC（角色刚好对应作者/编辑/审核/管理员）+ 审计（内容变更追溯）+ Webhook（发布触发构建）= **5000+ 行**
- **增量工程**：
  - 富文本字段类型（Markdown / TipTap / Slate）
  - 媒体库（图片 / 视频上传，需要对象存储集成）
  - 内容预览 / 草稿 / 版本历史
  - 工作流（草稿 → 审核 → 发布）
  - i18n 内容管理
  - SDK（GraphQL 或 REST）给前端框架（Next.js / Nuxt / Astro）调用
- **工程量**：**3-4 人月**
- **风险**：
  - 偏离主航道（"零代码 BaaS" vs "CMS"）
  - 与 Strapi / Directus / Payload 等成熟产品竞争
- **协同**：可独立；可作为 #1 的"垂直应用模板"之一

---

### 候选 9：表单 / 低代码内部应用平台

- **一句话定位**：拖拽生成内部审批 / 数据录入 / 简单 CRUD 应用，后端自动用 Auto API
- **谁会用**：业务方、IT 支持团队、行政 HR 等"找不到开发"的场景
- **存量利用**：Auto API（100%）+ RBAC + 审计 + Webhook = **5000+ 行**
- **增量工程**：
  - 表单设计器（拖拽 / 字段类型 / 校验规则 / 联动）
  - 应用引擎（生成 SPA，无需编译）
  - 流程编排（简单审批：申请 → 审批 → 通过/拒绝）
  - 移动端适配
  - 仪表板组件（图表 / 列表 / 详情）
- **工程量**：**4-5 人月**
- **风险**：
  - 工程量在 10 个候选里最大
  - 与钉钉宜搭 / 飞书多维表格 / Retool 直接竞争
- **协同**：可独立；最佳协同是与 #1（共享项目模型）

---

### 候选 10：实时数据推送 BaaS

- **一句话定位**：客户端 WebSocket 订阅 → 数据库变更实时推送到浏览器（类 Supabase Realtime）
- **谁会用**：需要"数据库即时推送"的场景（仪表盘 / 协作工具 / 多人在线）
- **存量利用**：realtime（211 行）+ events + redis_pubsub + Webhook 触发链 = **600+ 行**
- **增量工程**：
  - 订阅协议标准化（参考 Supabase Realtime / Phoenix Channels）
  - 客户端 SDK（JS/TS、Python、Flutter）
  - 订阅级 RBAC（订阅时校验 + 推送前过滤）
  - 大量并发连接的连接管理（按租户隔离 WS 池）
  - 离线消息补推
- **工程量**：**2.5-3 人月**
- **风险**：
  - 大量长连接对 Rust 服务的资源压力（Tokio 能扛，但要测）
  - 离线推送语义复杂（at-most-once / at-least-once）
- **协同**：是 #1 / #4 / #5 的扩展能力，可作为附加功能而非独立产品

| **#7 SSO 中台** | 叠加 | – | 共享 | – | – | – | – | – | – | – |
| **#8 CMS** | 上层 | – | 子集 | – | – | 叠加 | – | – | – | – |
| **#9 低代码** | 上层 | – | 子集 | – | – | 叠加 | – | – | – | – |
| **#10 实时推送** | 上层 | – | – | – | 共享 | – | – | – | – | – |

> **图例**：上层=依赖前者作底座；子集=可作为前者的功能模块；共享=共用基础设施；叠加=横向能力可附加；互补=用户/场景互补；–=无显著关系

### 3.3 互斥提醒

- **#7 SSO 中台**与其它候选互斥度低，但**作为独立产品的商业价值低**（市场已经有 Keycloak/Authing），建议作为 OneBase 内嵌能力，不单独立项
- **#8 CMS / #9 低代码**与 #1 零代码后端的差异更多在"前端形态"，**不要同时做两个，否则重复造轮子**
- **#2 PG 治理**与 #1 在"建表"功能上重叠，需要前期约定好"DBA 视角"vs"开发者视角"的边界

## 4. 组合菜谱（5 套，按目标客户画像）

### 菜谱 A：「开发者赋能」组合（推荐用于"内部 BaaS"定位）

- **包含**：#1 零代码后端 + #3 审计 + #6 AI 助手
- **总工程量**：5-6 人月
- **适合谁**：客户主要是开发者团队、需要快速搭建后端
- **GA 后效果**：开发者 30 分钟从 0 到一个完整后端，自带 RBAC / 审计 / AI 帮写 SQL
- **覆盖原 ROADMAP 中**：第一阶段 + 第二阶段 + 部分第三阶段

### 菜谱 B：「数据治理」组合

- **包含**：#2 PG 治理 + #3 审计合规 + #6 AI 慢查询诊断
- **总工程量**：5-6 人月
- **适合谁**：客户已有大量 PG 库，DBA / 运维 / 安全是主要用户
- **GA 后效果**：所有 PG 库统一管控、慢查询自动诊断、合规报表一键导出

### 菜谱 C：「数据资产化」组合

- **包含**：#1 零代码后端 + #4 数据资产 + #5 逆向 ETL
- **总工程量**：6-7 人月
- **适合谁**：有数据中台诉求、跨部门数据共享场景
- **GA 后效果**：表 → 资产 → 订阅 → 计量 → 推送下游 一条龙

### 菜谱 D：「内容运营」组合

- **包含**：#1 零代码后端 + #8 CMS + #10 实时推送
- **总工程量**：**7-9 人月**（CMS 工程量大；可以裁掉 #10 缩到 5-7 人月）
- **适合谁**：媒体、内容平台、需要"管理后台 + 前台展示"的场景
- **GA 后效果**：内容编辑 → 实时同步到前台

### 菜谱 E：「最小切入」组合（3 个月内可交付）

- **包含**：#1 零代码后端（裸最小集，仅项目+建表+RBAC可视化） + #3 审计（简化版，仅大盘+导出）
- **总工程量**：**3-4 人月**（裸最小集 = #1 砍掉表设计器/模板/邀请，仅 1.5-2 人月；#3 简化 1-1.5 人月；端到端联调 0.5 人月）
- **适合谁**：想先看效果再决定下一步、预算有限、客户场景未完全锁定
- **GA 后效果**：开发者能用、有审计、其余功能后续按需增量
- **价值**：是其它所有菜谱的"公共基础"，做完再选 A/B/C/D 都不返工

## 5. 决策建议框架

不替你拍板，给你"如果...就考虑..."的判断流程：

```
                 ┌─────────────────────────────┐
                 │ 客户主要用户是谁？           │
                 └──────────────┬──────────────┘
                                │
           ┌────────────────────┼────────────────────┬──────────────────┐
           ▼                    ▼                    ▼                  ▼
      开发者为主          DBA/运维为主          数据团队为主         内容/业务为主
           │                    │                    │                  │
           ▼                    ▼                    ▼                  ▼
       菜谱 A              菜谱 B              菜谱 C              菜谱 D
   (开发者赋能)         (数据治理)         (数据资产化)          (内容运营)
```

**横向叠加问题**：
- 客户付费意愿强 / LLM 场景成熟 → **加 #6 AI 助手**
- 客户已有 SSO 系统 → **#7 不做**
- 客户场景多样、还在探索 → **先做菜谱 E**（3 个月最小切入），再按反馈选 A/B/C/D

**预算 / 团队规模导向**：
- 1 个 2-3 人小队 6 个月内交付 → 菜谱 A 或 E
- 1 个 4-5 人团队 9 个月内交付 → 菜谱 A + #6 AI
- 2 个团队并行 → 菜谱 A + 菜谱 B 同步推进（共享 #3 审计基础设施）

## 6. 不易做（不推荐）的方向 + 原因

| 方向 | 不推荐原因 | 替代方案 |
|---|---|---|
| **自动化部署 / IaC 平台** | 内核 0 存量；客户基本都已有 GitOps / Argo CD 实践；自研要 6+ 人月 | 提供 Helm Chart 让客户对接其现有 GitOps |
| **多 Region / 跨集群编排** | 客户场景未要求；引入会拖慢主线 8+ 人月 | v3+ 再考虑 |
| **PG 自动 failover** | 让 [CloudNativePG](https://cloudnative-pg.io/) 干，他们做了 5 年 | 部署文档推荐 CloudNativePG |
| **全功能 APM** | Prometheus/Grafana/Loki 比自研强 10 倍 | 暴露 `/metrics` 端点对接，写一份对接文档 |
| **通用 API 网关（管别人的 API）** | 偏离主航道；与 Kong/APISIX 直接竞争 | 不做 |
| **GraphQL / gRPC 端点** | 与 REST 主线冲突；客户没明确要；增加测试矩阵 | 不做 |
| **AI Agent 自主执行** | 安全风险高；私有化客户难接受 AI 自主改库 | 永远人工确认 |
| **区块链 / Web3 集成** | 与产品定位不符 | 不做 |

## 7. 既存技术债与潜在隐患（基于 commit log + README "🚦 必读" + 架构观察）

### 7.1 已知需要继续打磨的地方

| 隐患 | 来源 | 平台化时的影响 | 建议 |
|---|---|---|---|
| `JWT_SECRET` / `ENCRYPTION_KEY` 默认值会 panic | README 警告 | 私有化部署文档必须强调 | M8 部署文档头条 |
| 历史 base64 密码需 `migrate_passwords` 升级 | README "升级到 v2" | 老用户升级路径要测 | 升级脚本一并交付 |
| Redis 不可达时降级为"无缓存模式" | commit `b02b8db` | 平台化后大盘 / 限流会失效 | 监控里要标 Redis 状态 |
| `/query` `/transaction` 必须严格按租户路由 | commit `f2a971b` 修了"串库"漏洞 | 平台化让更多角色能查 SQL，串库风险放大 | 必加单元测试 + 集成测试 |
| `monitor_handlers` 在 PG 14+ 上的 NULL/NUMERIC 兼容 | commit `54def70` 修过 | 多 PG 版本时易复发 | 加 PG 12/14/16 矩阵测试 |
| 慢查询展示问题 | commit `bf3688f` 修过 | 大盘要持续验证 | 持续 |
| API Key 提权风险 | commit `911d895` 加固 | 数据资产平台开放 API Key 时再次面临 | 安全设计专项评审 |

### 7.2 架构层面的潜在瓶颈

| 瓶颈 | 触发条件 | 缓解 |
|---|---|---|
| 审计日志单表 | 单租户 QPS > 1k 时表会迅速膨胀 | 平台化前加分区表 |
| 多租户连接池总数上限 | 项目数 > 50 时 PG 端连接耗尽 | 引入 PgBouncer 或重新设计连接池 |
| Redis 单实例 | 多项目共享单 Redis 时是 SPOF | 文档建议 Sentinel/Cluster |
| 前端单 app 加载 | 加入工作空间后 bundle 会膨胀 | 改 Next.js 路由分包 |
| 没有 OpenAPI/Swagger | 平台化后第三方接入难 | 自动生成（已在原 ROADMAP §1.3） |
